# 版本更新（0.6.0 起）

资料库中的“应用更新”可手动检查、下载、查看真实字节进度、取消、重试和确认安装。启动及运行中的每 6 小时自动检查一次；检查不会自动下载、安装或中断音乐。下载时关闭面板不取消任务，资料库顶部仍显示进度。下载和完整性校验都完成后才显示安装/重载按钮。

**这是源码功能，不表示 0.6.0 已发布。** 已安装的旧版没有这套更新代码，需要先通过原渠道手动安装一个包含更新功能的版本。

## 各平台实际行为

- **Android**：从固定 GitHub 仓库下载通用 APK 到应用私有缓存。点击安装后再次校验文件，并检查包名、递增版本代码和当前 APK 签名证书一致性。然后才请求系统“允许此来源安装”或打开系统安装器。用户返回设置页后必须再次点击安装；不静默安装，不自动继续。
- **macOS**：从固定仓库下载适配当前架构的 DMG。点击“打开安装包”后通过 NSWorkspace 打开；下载文件必须带系统隔离属性。由用户在 DMG 窗口完成应用替换与重启。**尚未实现自动替换/重启**，不会去除 quarantine、关闭 Gatekeeper 或执行下载的脚本。
- **Web/PWA**：只检查当前网站自己的部署，按构建生成的清单下载并逐文件校验新版。完成后明确提示重载；只有用户确认才切换。显示实际收到的资源字节，不是模拟计时。重载会停止播放，目录权限/会话可能需重新选择。
- **iOS/iPadOS**：不能通过应用内下载 IPA 替换应用。界面说明使用原安装渠道（App Store/TestFlight）；仓库当前不提供签名 iOS 安装包。

## 原生发布与信任边界

固定元数据入口为 `https://api.github.com/repos/KingXcode/cloud-music/releases?per_page=30`，不要求登录、不内置 token。使用发布列表而不是忽略预发布版本的 `/latest`；当前项目所有预览发布都可成为候选。仅接受更高构建号且版本号不回退、支持当前架构的版本。

从 GitHub 的 release asset 元数据读取 `update-manifest.json` 的 SHA-256、大小和固定仓库下载地址，下载后验证清单。清单记录实际 APK/应用包版本、构建号、架构、文件名、大小和 SHA-256。再与 GitHub 为每个安装包返回的独立 digest/size 对照，最终验证收到的文件。缺少 digest、清单不匹配、重复同名资产、错误架构、超大文件、损坏、网络失败均不会触发安装。

仅允许 HTTPS 官方仓库 release 下载 URL 及 GitHub 的 `release-assets.githubusercontent.com` 跳转，不跟随任意外站跳转。原生下载流式写磁盘，不将完整安装包放进内存；只清理专用更新缓存中符合固定命名规则的旧更新文件。

**SHA-256 + HTTPS 是传输/发布完整性保护，不是独立的发行者签名。** GitHub 仓库/账号若被攻破，散列不能证明发布者身份。Android 由系统签名机制增加身份保护；macOS 当前仍是未 Developer ID 签名、未公证的预览 DMG，所以不启用自动安装。

### 构建流程

正常双平台发布工作流在 APK 和 macOS 构建完成后执行：

```sh
python3 scripts/create_update_manifest.py dist "$RELEASE_TAG"
```

从 `android-package.txt` 中的实际包信息及 `macos-version.json` 读取版本，验证标签对应实际包版本，拒绝任一平台版本不匹配或缺失产物。Android-only 发布以 `--android-only` 生成清单。GitHub 上传后必须确实返回每个 asset 的 SHA-256 digest，客户端才可使用。旧发布没有清单时不会被当成可下载更新。

每次原生发布必须递增 `pubspec.yaml` 的 `+build`。当前调试/测试 APK 签名可能随 CI runner 改变，**不同签名不能覆盖安装**。不要通过卸载/清空应用“自动解决”，否则可能丢失应用资料；正式可靠更新前需由开发者配置妥善保管且跨版本一致的生产签名。

网页的每次内容或配置变更都必须递增构建号。同一版本/构建号出现不同内容 ID 无法安全排序，因此拒绝启用；更低版本或更低构建号同样被拒绝。

网页构建后执行：

```sh
flutter build web --release --no-web-resources-cdn --base-href /cloud-music/
node scripts/prepare_web_updates.cjs build/web
```

生成网站自己的更新清单、不可变资源及服务工作线程支持。不要跳过第二步或单独覆盖部分资源。只有通过更新器完整下载并启用的版本会被保留到应用缓存。首次访问且未缓存的页面，如果下一次部署删除了旧的不可变资源目录，尚未读取的资源可能返回 404；系统不会悄悄混用两个版本。

首次迁移到更新机制之前的旧页面可能仍受原 Flutter service worker / CDN 缓存影响，需要正常重载。没有旧版本源代码的客户端不可能被新的应用按钮主动更新。

### 多标签页启用与缓存保留

网页更新要求浏览器支持 Web Locks。启用时使用按网站作用域隔离的独占锁，重新读取持久化的全局已启用版本，再验证版本/构建号不会回退。锁跨旧/新 service worker 实例共享；过期标签页不能将新版本覆盖回旧版本。每个同源运行页面还会报告实际执行的构建，持久化只升不降的版本/构建号下限：即使从未启用过离线缓存，也不能把已经观察到的网络新版退回旧下载。若较新页面稍后才完成注册，之后的导航同样不会继续使用低于该下限的旧 active 缓存，而会读取当前网络入口。此时若新版尚未下载且网络离线，不会为了离线可用而偷偷回退。相同内容 ID 已启用时保持原缓存引用。每个标签页的下载另持有独立锁，防止 worker 替换时覆盖仍在使用的下载记录。

正常保留范围为：当前已启用版本 + 每个仍运行标签页需要的版本 + 最多一个不再运行的历史版本；每个活动标签页可有一个准备中下载。关闭标签页的准备缓存、孤立半成品/完整缓存和较老的闲置版本会清理。每个页面注册当前构建，导航中尚未出现在客户端列表的页面有 30 秒保护期。若存在无法识别的旧页面或损坏状态，先保留已安装缓存以免打断播放，关闭或重载这些页面后恢复清理。因此这是对闲置历史版本的有界保留，不承诺无论打开多少不同版本标签页都只占固定大小。不会清理其他应用缓存或音乐资料。

参考：[Web Locks 跨上下文互斥语义](https://www.w3.org/TR/web-locks/)。真实浏览器行为仍在下方未验证范围内。

## macOS 接近 Codex 的下一步

可靠的“下载后安装并重启”应集成成熟的 Sparkle 2，包括独立 EdDSA 更新签名、公钥固定、HTTPS appcast、沙盒 Installer XPC 服务及其准确授权，以及对最终包的签名校验、失败回滚和重启验证。面向公开用户还应使用 Developer ID、Hardened Runtime 和 Apple 公证。

本次没有创建或保存私钥、签名证书或 Apple 凭据，也没有扩大沙盒权限。没有这些配置时不能把打开 DMG 说成自动更新。

## 验证范围

自动化覆盖版本/清单/散列、取消和重复点击、下载/安装状态、窄屏面板、网页资源的部分失败与切换保护，以及原生路径和身份校验策略。最终执行情况以本次交付报告为准。Linux 工作区不能替代 macOS/Xcode、Android SDK 的编译及真实设备测试。

发布前仍须验证：

1. 同一 APK 签名的新旧版本覆盖安装、证书不同拒绝、未知来源拒绝/返回、安装取消、低空间和断网。
2. macOS 沙盒中下载、隔离属性、DMG 挂载、Gatekeeper、不同 CPU 架构和手动替换；不能以源码或单元测试推断签名/公证已完成。
3. HTTPS 实站两个连续网页版本的下载进度、取消后重试、校验失败、重载前继续播放、多标签页、断网和浏览器存储限额。浏览器可回收离线缓存，离线包并非永久保留承诺。
